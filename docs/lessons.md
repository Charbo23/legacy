# 经验总结

## AI 与人工配合

- AI 负责结合需求、源码、现场信息和日志制定方案、初步分析候选原因，并实现代码和自动化验证。
- 人负责确定关键方向并实际上手验收，尤其判断样式、交互和使用便捷性。
- AI 完成实现和自动化验证只表示可以进入人工验收，不能作为最终交付结论。

## 测试与验收

- 做题、支付、分享等关键链路必须人工操作。
- 普通 Web 变更至少测试 iOS、Android 和微信端。
- 只有发布新 App 包时才执行完整真机和云测矩阵。
- 功能正确但交互不合理也不能通过，例如返回键未先关闭弹出层、路由跳转卡顿、请求明显慢或存在冗余请求。

## A/B 放量与收口

1. 功能进入待上线阶段后即可全量切到 B。
2. 全量 B 连续 3 天无问题后移除 A/B 分流，观察重点是用户反馈，其他证据按需求判断。
3. 收口时删除所有分组、分流、实验参数和双分支调用代码。
4. 保留 B 文件，用 B 的完整内容覆盖 A 文件，并把调用位置统一改回 A 文件；B 文件不要求同期删除。

接口迁移不能只比较页面或顶层响应。至少检查前端实际消费字段、错误语义、副作用、共享缓存格式，以及 A 写 B 读、B 写 A 读的即时结果。

## 跨端兼容

- 除了必须依赖新版 App 的能力，尽可能兼容旧版。新版专属能力不可用时，旧版应隐藏或拒绝进入，不能报错。
- `plus.storage` 等跨端数据要保留旧 key、类型和空值语义；增加新 key 通常比改变旧 key 更安全。
- 离线开关、ready 信号、缓存版本和失败回退各自只保留一个事实源，避免 Web、Service Worker 和 App 壳互相覆盖状态。
- 构建环境、cloudtest、DCloud debug、入口域名和 APK 身份必须一致，新包验收要从运行态确认实际域名和版本。

## 发布与权限

- 普通 Web 变更沿用正常源码发布流程；完整真机和云测只在新 App 包发布时执行。
- DCloud 交接的关键不是能看到应用，而是接手人能使用自己的组织身份完成 uni-app 构建。
- PC Electron 打包仓历史文档出现过明文 Apple 公证凭据。凭据进入 Git 历史即视为泄漏，必须在 Apple 侧轮换；只删除当前文件不能完成处置。

## 内容维护

- 本项目只记录接手后实际需要使用的项目知识，不复制源码可以直接说明的细节。
- 从源码得出的关系要标明仍需现网确认的部分，例如 PC 端当前实际分发的是哪一种壳。
- 小护排班业务规则、账号注销业务规则和基础设施运维不扩展进本文档；遇到具体需求时按当期业务口径处理。
